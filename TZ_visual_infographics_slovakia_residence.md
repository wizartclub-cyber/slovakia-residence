# Технічне завдання: візуальні пояснення та інфографіка для «Проживання в Словаччині»

**Проєкт:** https://wizartclub-cyber.github.io/slovakia-residence/uk/  
**Дата аудиту:** 09.09.2026  
**Мета релізу:** скоротити час пошуку потрібної процедури, зробити строки, документи, платежі й послідовність дій зрозумілими без спрощення юридичного змісту.

## 1. Контекст і проблема

Сайт має сильну змістову структуру: 23 маршрути, опитувальник, окремі сторінки процедур, джерела та позначення стану юридичної перевірки. Однак ключова інформація переважно подана текстом. На довгих сторінках користувачеві складно швидко відповісти на п’ять практичних питань:

1. Чи підходить мені цей маршрут?
2. Що робити і в якій послідовності?
3. Які документи потрібні та скільки вони чинні?
4. Скільки часу й грошей потрібно?
5. Які дії виконати після отримання рішення?

Інфографіка має бути функціональним інтерфейсом, а не декором. Вона не повинна створювати нових юридичних тверджень або приховувати застереження.

## 2. Принципи дизайну

- **Progressive disclosure:** спочатку короткий візуальний підсумок, далі повний юридичний текст і джерела.
- **Один зміст — одне джерело даних:** графіка генерується з тих самих структурованих даних, що й текст маршруту.
- **Колір не є єдиним носієм змісту:** статус завжди має іконку та текст.
- **Без юридично небезпечного «100%»:** не показувати оцінку шансів, гарантії результату чи категоричні висновки.
- **Mobile first:** усі модулі працюють від 320 px без горизонтального прокручування.
- **Друк:** важлива графіка повинна залишатися зрозумілою у чорно-білому PDF/друці.
- **Дві мови:** однакова функціональність для `/uk/` і `/sk/`; жодного тексту всередині растрових зображень.

## 3. Обсяг MVP — пріоритет P0

### 3.1. Головна: «Як працює довідник»

Додати під головним CTA горизонтальний процес із 4 кроків:

1. **Відповідаєте на 6 питань** — іконка перемикачів.
2. **Отримуєте відповідні маршрути** — іконка розгалуження.
3. **Збираєте документи** — іконка папки/чекліста.
4. **Подаєте до компетентного органу** — іконка державної будівлі.

На мобільному — вертикальний список. Кожен крок має 1 коротке речення; блок не повинен виглядати як гарантія прийняття заяви.

### 3.2. Головна: візуальна карта типів перебування

Замість лише текстового переліку показати 6 карток-категорій:

- в’їзд і короткострокове перебування;
- тимчасове проживання;
- постійне/довгострокове проживання;
- толероване перебування;
- міжнародний/тимчасовий захист;
- вільний рух громадян ЄС.

Картка містить іконку, назву, кількість доступних маршрутів і посилання на відфільтрований список. Не використовувати прапори для позначення юридичних категорій.

### 3.3. Опитувальник: прогрес і видиме дерево рішення

Замінити напис «Питання N з 6» на доступний progress bar:

- заповнена частина + `N/6` + коротка назва поточного етапу;
- `aria-valuemin`, `aria-valuemax`, `aria-valuenow`;
- попередні відповіді показувати у блоці «Ваша ситуація» як компактні chips;
- кожен chip можна змінити без повного перезапуску;
- перед результатом показати коротке резюме вибраних умов.

Не показувати користувачеві повне технічне дерево правил. Додати мінісхему: **громадянство → поточний статус → мета → місце подання → результат**.

### 3.4. Список маршрутів: картки та фільтри

Перетворити кожний маршрут на картку зі стабільною структурою:

- іконка категорії;
- назва;
- тип статусу;
- орієнтовний строк рішення, якщо підтверджений;
- базовий збір «від …», якщо підтверджений;
- статус юридичного рев’ю;
- дата стану права;
- кнопка «Відкрити маршрут».

Додати фільтри: категорія, громадянин ЄС/третя країна/тимчасовий захист, мета, перше подання/поновлення, статус юридичної перевірки. Фільтри мають синхронізуватися з URL query parameters, щоб результат можна було надіслати посиланням.

### 3.5. Сторінка маршруту: «Паспорт процедури»

Одразу після заголовка додати summary panel із 6 полями:

| Поле | Приклад для §22 |
|---|---|
| Тип | Тимчасове проживання |
| Підстава | Підприємницька діяльність |
| Строк дозволу | до 3 років |
| Строк рішення | 90 днів; окремий висновок — до 60 днів |
| Куди подавати | поліція / закордонна установа — лише коли підтверджено |
| Стан даних | дата права + статус юридичного рев’ю |

Якщо значення не підтверджене, показати «Потребує перевірки», а не пропуск чи припущення.

### 3.6. Сторінка маршруту: процес у вигляді stepper/timeline

Згенерувати вертикальну шкалу етапів:

1. перевірити право і місце подання;
2. підготувати документи;
3. подати заяву та сплатити збір;
4. очікувати рішення / доповнити заяву;
5. отримати картку;
6. виконати післярішенневі обов’язки.

Для §22 окремо позначити бізнес-план, два різні рахунки та обов’язки протягом 30 днів після картки. Кожен вузол timeline повинен мати anchor link на повний розділ сторінки.

### 3.7. Документи: візуальний чекліст і шкала чинності

Для кожного документа показувати:

- checkbox, назву українською і словацькою;
- статус: обов’язковий / умовний / виняток;
- строк чинності як badge: «≤ 90 днів», «≤ 30 днів», «без зазначеного строку»;
- момент, коли документ має бути чинним: «на день подання» або інший підтверджений момент;
- розгортання «Коли потрібен / винятки / джерело»;
- кнопку «Додати дату видачі» для локального розрахунку крайньої дати (P1).

Стан checkbox зберігати лише локально (`localStorage`) з чітким повідомленням; не збирати персональні дані. Додати «Скинути чекліст».

### 3.8. Строки: інтерактивна шкала

Додати блок «Ключові строки» з відносними точками:

- до подання: документи не старші за N днів;
- день подання;
- строк рішення;
- після картки: N днів на страхування/медичний висновок;
- можливе продовження строку — лише якщо воно прямо підтверджене.

Не об’єднувати паралельні строки в одну арифметичну суму. Наприклад, 90 днів поліції та 60 днів для висновку міністерства не показувати як «150 днів», якщо закон прямо цього не встановлює.

### 3.9. Збори: порівняльна таблиця-калькулятор

Показати картки/таблицю каналів подання:

| Канал | Базовий збір | Електронний | Рівень підтвердження |
|---|---:|---:|---|
| Поліція | 330 € | 280 € | джерело/статус |
| Закордонна установа | 350 € | 300 € | «не підтверджено» до рев’ю |

Не називати це остаточною вартістю. Нижче окремо показувати можливі звільнення та дискреційні знижки. Суми беруться з даних маршруту; жодних hard-coded значень у UI-компоненті.

### 3.10. Джерела: індикатор надійності, а не технічний список

Для кожного джерела сформувати статусну смугу з чотирма незалежними ознаками:

- офіційне / вторинне;
- URL перевірено / не перевірено;
- snapshot збережено / відсутній;
- чинне / потенційно застаріле / майбутня редакція.

Показувати SHA-256 у розгорнутій технічній секції, а не як головний елемент картки. Додати легенду статусів і фільтр «потребує перевірки».

## 4. Наступний етап — P1

1. **Порівняння до 3 маршрутів:** строк, збір, документи, право на роботу, тривалість дозволу, післярішенневі дії.
2. **Локальний календар документів:** користувач вводить дату планованого подання; система показує найранішу безпечну дату замовлення документів і попереджає про ризик прострочення. Результат не називати юридичною гарантією.
3. **Карта органів подання:** лише після наповнення перевіреними адресами, територіальною компетенцією та офіційними URL. До цього карту не створювати.
4. **Візуальний гід бланка:** номер поля → пояснення → приклад без реальних персональних даних; реалізувати лише після фіксації конкретної версії PDF.
5. **«Що буде далі» після результату опитувальника:** рекомендований маршрут, альтернативи та причини, чому інші маршрути не підійшли.

## 5. Що не робити

- не використовувати стокові фото людей, прапори, герби або фото поліції як декоративний фон;
- не створювати кругові діаграми без числового змісту;
- не показувати «відсоток готовності заяви» лише за відміченими документами;
- не приховувати неперевірені дані за зеленим кольором загальної картки;
- не вбудовувати юридичні тексти в SVG/PNG;
- не дублювати контент вручну в компонентах;
- не застосовувати Mermaid у production UI; графіку реалізувати семантичним HTML/CSS/SVG.

## 7. Розширення моделі даних

Мінімальні поля маршруту:

```ts
type Verification = 'verified' | 'unverified' | 'stale' | 'future';

interface RouteVisualData {
  category: string;
  applicantGroups: string[];
  permitDuration?: { value: number; unit: 'days'|'months'|'years'; sourceId: string };
  decisionDeadlines: Array<{ label: string; days: number; relation: 'parallel'|'sequential'|'unknown'; sourceId: string }>;
  stages: Array<{ id: string; order: number; title: string; anchor: string; deadlineDays?: number; sourceId?: string }>;
  documents: Array<{
    id: string;
    title: { uk: string; sk: string };
    requirement: 'required'|'conditional'|'exception';
    validityDays?: number;
    validityMoment?: 'submission'|'issuance'|'decision'|'other';
    sourceIds: string[];
  }>;
  fees: Array<{ channel: string; amount: number; currency: 'EUR'; electronicAmount?: number; verification: Verification; sourceIds: string[] }>;
  legalReview: 'not-reviewed'|'in-review'|'reviewed';
  lawStateDate: string;

```

Додати schema validation під час build. Збірка повинна падати, якщо елемент графіки посилається на відсутнє джерело або якщо сума/строк не має `sourceId`.

## 8. Візуальна система

- Використати наявну типографіку й кольори сайту; додати максимум один акцентний колір.
- Семантичні статуси: підтверджено, увага, не перевірено, прострочене джерело. Кожен має текст + іконку + колір.
- Іконки: одна бібліотека outline-іконок або власні прості SVG; `aria-hidden="true"` для декоративних.
- Мінімальний контраст WCAG AA; focus indicator не менше 2 px.
- Анімації 150–250 ms; повністю вимикати через `prefers-reduced-motion`.
- Максимальна ширина текстового рядка 70–75 символів; довгі юридичні пояснення не поміщати у tooltip.

## 9. Доступність і семантика

- WCAG 2.2 AA як ціль.
- Timeline — впорядкований список; чекліст — справжні checkbox; фільтри — form controls.
- Tooltip не повинен бути єдиним способом доступу до інформації; важливі пояснення відкриваються кнопкою/`details`.
- Усі інтерактивні елементи доступні клавіатурою.
- Після зміни фільтрів і результатів опитувальника використовувати коректний `aria-live`, без надмірних оголошень.
- Мінімальна touch target 44×44 px.

## 10. Responsive і print

- Breakpoints визначити за контентом, орієнтовно: 640 / 960 / 1200 px.
- На вузьких екранах таблиці перетворюються на вертикальні картки, а не створюють горизонтальний scroll.
- Для `@media print`: прибрати навігацію, кнопки та фільтри; розгорнути потрібні деталі; друкувати URL/ідентифікатор джерела; не розривати картку документа між сторінками.
- Користувацькі відмітки чекліста повинні бути видимі при друці.

## 11. Аналітика без персональних даних

Якщо аналітика вже використовується, додати лише агреговані події:

- старт/завершення finder;
- крок, на якому припинили;
- відкриття маршруту;
- використання фільтра;
- друк чекліста;
- відкриття джерела.

Не передавати відповіді користувача як повний профіль і не збирати назви документів, дати видачі чи інші персональні відомості.

## 13. Критерії приймання

1. На кожній наповненій сторінці маршруту над fold або одразу під заголовком видно: тип, строк дозволу, строк рішення, орієнтовний збір і статус перевірки.
2. Кожен строк і кожна сума в графіці мають посилання на джерело в даних.
3. Непідтверджене значення явно позначене і ніколи не стилізоване як підтверджене.
4. Опитувальник показує прогрес, дозволяє переглянути/змінити попередню відповідь і не надсилає дані на сервер.
5. Чекліст працює без реєстрації, локально зберігається, скидається і коректно друкується.
6. Усі модулі функціональні при 320 px, 768 px і 1440 px.
7. Повний сценарій доступний лише клавіатурою; Lighthouse Accessibility ≥ 95 на ключових сторінках.
8. Lighthouse Performance ≥ 90 на мобільному для production build; нові SVG та JS не погіршують LCP понад 200 ms від baseline.
9. Немає горизонтального прокручування сторінки при 320 px.
10. Українська і словацька версії мають однаковий набір компонентів; відсутні hard-coded UI-тексти.
11. Друк типової процедури не містить порожніх блоків, обрізаного тексту або прихованих за accordion важливих умов.
12. Unit-тести покривають трансформацію даних строків/зборів; E2E — finder, фільтри, чекліст, print view і мовне перемикання.

## 14. Definition of Done

- реалізація пройшла code review;
- schema validation і тести виконуються в CI;
- перевірено три контрастні режими: стандартний, forced colors, чорно-білий друк;
- юридичний редактор підтвердив, що графіка не змінює зміст текстових правил;
- оновлено документацію про додавання нового маршруту та його візуальних даних;
- сторінки не містять placeholder `[НАЗВА ОРГАНІЗАЦІЇ]` перед публічним релізом.

## 15. Очікуваний результат

Користувач за 10–15 секунд розуміє структуру обраного маршруту, бачить критичні строки й документи, а потім може перейти до повного юридичного пояснення та першоджерела. Візуальний шар не замінює правовий текст, а служить навігацією по ньому.
